# 本地微调结果测试指导书

## 1. 目标

在真实 SO-100/SO-101 上比较：

```text
基础模型: /path/to/we_smolvla/models/smolvla_base
微调模型: 本地动作专家检查点
```

本阶段的目标是建立可复现、可比较、包含失败案例的测试记录。

## 2. 测试原则

必须满足：

- 微调模型和基础模型使用同一机械臂、摄像头、任务文本和初始状态协议。
- 测试 episode 不参与训练。
- 记录所有 episode，不删除失败 episode。
- 同一条件至少运行 20 次，条件允许时运行 30 次。
- 随机化基础模型和微调模型的执行顺序，减少环境漂移。
- 任何参数改变都重新建立新的测试批次。

## 3. 测试分级

### 第一级：空载检查

机械臂不接触目标物体，或物体远离运动路径。只检查：

- 动作方向。
- 关节是否剧烈跳动。
- 是否出现异常位姿。
- 推理延迟。

### 第二级：有人值守短测试

每个模型执行 3 至 5 个 episode。操作者保持急停可用。

### 第三级：正式测试

基础模型和微调模型各执行同一组 20 至 30 个测试 episode。


测试期间不要更新 LeRobot、PyTorch、驱动或校准文件。

LeRobot `0.4.3` 不提供 `lerobot-rollout`。真实机械臂策略执行使用：

```text
lerobot-record + --policy.path
```

该方式会同时：

- 从策略产生动作。
- 将动作发送给 follower。
- 将观测、动作和任务文本记录为 LeRobotDataset。

如果需要在评估时查看 action chunk 和实际执行动作，在策略模式命令中加入：

```bash
--display_action_trace=true
```

该参数会打开一个独立于 Rerun 的 Matplotlib 窗口，同时显示：

- 当前 action queue 的剩余动作数量。
- 每个动作维度的模型预测值，使用虚线。图形数量由 `action_features` 自动确定。
- 经过 `max_relative_target` 截断后实际发送给机械臂的动作，使用实线。

监控窗口只读取策略队列和发送动作，不修改 LeRobotDataset 字段，也不改变控制逻辑。
它可以与 `--display_data=true` 同时使用。若当前环境没有可用图形显示，监控进程会
记录警告并使用 Agg 后端，评估本身仍会继续执行。

### Figure 3 对应的异步 action queue

`lerobot-record --policy.path=...` 使用同步推理。同步模式下 `select_action()` 每次
只从策略队列取出当前要执行的动作，不能表示 SmolVLA Figure 3 中异步推理的
`action queue size`。如果要得到 Figure 3 的纵轴含义，需要使用仓库的异步客户端，
并打开 `--display_action_trace=true`。

例如 `--policy.n_action_steps=1` 时，策略仍可能计算一个长 action chunk，但同步
队列只保留前 1 个动作，所以每次出队后队列为 0。这个现象不能解释为模型每次只输出
1 个动作，也不能通过它得到 Figure 3 的异步队列范围。

终端 1 启动策略服务器：

```bash
conda activate lerobot_043
cd /path/to/we_smolvla

python -m lerobot.async_inference.policy_server \
  --host=127.0.0.1 \
  --port=8080
```

终端 2 启动异步客户端：

```bash
conda activate lerobot_043
cd /path/to/we_smolvla

export CHECKPOINT=/path/to/we_smolvla/outputs/train/smolvla_so101_expert_original_v1/checkpoints/016000/pretrained_model

python -m lerobot.async_inference.robot_client \
  --server_address=127.0.0.1:8080 \
  --robot.type=so101_follower \
  --robot.port=/dev/ttyACM1 \
  --robot.id=so101_follower_main \
  --robot.cameras="{ camera1: {type: opencv, index_or_path: 0, width: 640, height: 480, fps: 30}, camera2: {type: opencv, index_or_path: 1, width: 640, height: 480, fps: 30} }" \
  --task="Pick up the blue cube and place it in the box." \
  --policy_type=smolvla \
  --pretrained_name_or_path="${CHECKPOINT}" \
  --policy_device=cuda \
  --actions_per_chunk=50 \
  --chunk_size_threshold=0.5 \
  --aggregate_fn_name=weighted_average \
  --display_data=true \
  --display_action_trace=true
```

上面的端口按当前设备枚举写为 `/dev/ttyACM1`。每次重启或重新插拔后应先用
`lerobot-find-port` 或系统串口列表确认 follower 的实际端口。

这里的 `actions_per_chunk` 对应 SmolVLA Figure 3 中的 `n`，
`chunk_size_threshold` 对应 `g`。监控窗口横轴使用控制步：

- 顶部曲线是每次出队前记录的 action queue size。
- 每个动作维度的虚线是服务器本次返回的原始 action chunk。
- 每个动作维度的实线是 `robot.send_action()` 实际执行值的轨迹。
- 窗口由独立 Matplotlib 进程显示，不依赖 Rerun。
- `display_data=true` 会把客户端读取到的所有 observation 图像发送到 Rerun，因此
  `camera1` 和 `camera2` 可以同时显示。

当前 `RobotClient` 不负责生成 LeRobotDataset。需要同时保存可训练 episode 时，
仍使用前面的 `lerobot-record` 命令；需要精确复现 Figure 3 的异步队列行为时，
使用上面的 `RobotClient` 命令。

## 5. 安全参数

首次测试建议：

```bash
--robot.max_relative_target=5 \
--display_data=true
```

`max_relative_target=5` 只是保守起点。应根据真实关节运动范围逐步调整。

首次测试必须准备：

- 物理急停。
- 电源快速断开方式。
- 清空工作空间。
- 物体位于低风险位置。
- 摄像头线缆不会被机械臂拉动。

## 6. 基础模型对照

两摄示例：

```bash
conda activate lerobot_043
cd /path/to/we_smolvla

RUN_STAMP=$(date +%m%d_%H%M%S_%3N)
DATASET_NAME=eval_so101_pick_blue_cube_base_${RUN_STAMP}

lerobot-record \
  --robot.type=so101_follower \
  --robot.port=/dev/ttyACM0 \
  --robot.id=so101_follower_main \
  --robot.cameras="{ camera1: {type: opencv, index_or_path: 0, width: 640, height: 480, fps: 30}, camera2: {type: opencv, index_or_path: 1, width: 640, height: 480, fps: 30} }" \
  --robot.max_relative_target=5 \
  --policy.path=/path/to/we_smolvla/models/smolvla_base \
  --policy.device=cuda \
  --policy.n_action_steps=10 \
  --policy.empty_cameras=1 \
  --dataset.repo_id=local/${DATASET_NAME} \
  --dataset.root=/path/to/we_smolvla/datasets/eval/${DATASET_NAME} \
  --dataset.single_task="Pick up the blue cube and place it in the box." \
  --dataset.fps=30 \
  --dataset.num_episodes=3 \
  --dataset.episode_time_s=30 \
  --dataset.reset_time_s=15 \
  --dataset.video=true \
  --dataset.video_encoding_batch_size=1 \
  --dataset.num_image_writer_threads_per_camera=4 \
  --dataset.push_to_hub=false \
  --display_data=true \
  --display_action_trace=true
```

`RUN_STAMP` 的格式为 `月日_时分秒_毫秒`，例如
`0918_131530_472`。每次重新启动评测都会生成新的数据集目录，不会覆盖之前的
批次。只有对同一批次续录时才必须继续使用原来的 `DATASET_NAME`。

三摄时删除：

```bash
--policy.empty_cameras=1
```

并在 `--robot.cameras` 中加入 `camera3`。

## 7. 微调模型测试

本示例固定使用 `16000` 步检查点：

```text
/path/to/we_smolvla/outputs/train/smolvla_so101_expert_original_v1/checkpoints/016000/pretrained_model
```

先确认检查点文件存在：

```bash
test -f /path/to/we_smolvla/outputs/train/smolvla_so101_expert_original_v1/checkpoints/016000/pretrained_model/config.json
test -f /path/to/we_smolvla/outputs/train/smolvla_so101_expert_original_v1/checkpoints/016000/pretrained_model/model.safetensors
```

再执行策略驱动录制。评测数据名称包含 `016000`，防止覆盖其他检查点的测试结果：

```bash
conda activate lerobot_043
cd /path/to/we_smolvla

export CHECKPOINT=/path/to/we_smolvla/outputs/train/smolvla_so101_expert_original_v1/checkpoints/016000/pretrained_model

RUN_STAMP=$(date +%m%d_%H%M%S_%3N)
DATASET_NAME=eval_so101_pick_blue_cube_expert_016000_${RUN_STAMP}

lerobot-record \
  --robot.type=so101_follower \
  --robot.port=/dev/ttyACM0 \
  --robot.id=so101_follower_main \
  --robot.cameras="{ camera1: {type: opencv, index_or_path: 0, width: 640, height: 480, fps: 30}, camera2: {type: opencv, index_or_path: 1, width: 640, height: 480, fps: 30} }" \
  --robot.max_relative_target=5 \
  --policy.path="${CHECKPOINT}" \
  --policy.device=cuda \
  --policy.n_action_steps=10 \
  --policy.empty_cameras=1 \
  --dataset.repo_id=local/${DATASET_NAME} \
  --dataset.root=/path/to/we_smolvla/datasets/eval/${DATASET_NAME} \
  --dataset.single_task="Pick up the blue cube and place it in the box." \
  --dataset.fps=30 \
  --dataset.num_episodes=3 \
  --dataset.episode_time_s=30 \
  --dataset.reset_time_s=15 \
  --dataset.video=true \
  --dataset.video_encoding_batch_size=1 \
  --dataset.num_image_writer_threads_per_camera=4 \
  --dataset.push_to_hub=false \
  --display_data=true \
  --display_action_trace=true
```

不同检查点、不同参数和不同启动时间必须使用不同的 `RUN_STAMP`。如果要比较多个
检查点，可以在名称中保留步骤号，例如：

```text
eval_so101_pick_blue_cube_expert_016000_0918_131530_472
```

LeRobot `0.4.3` 要求带策略的评测数据集名称以 `eval_` 开头。`local/eval_...`
满足该要求。

不要把 `--dataset.repo_id` 写成 `local/rollout_...`，也不要使用：

```text
--strategy.type=base
--strategy.type=episodic
--inference.type=rtc
--dataset.no_stamp=true
```

这些参数属于不兼容的版本接口。

## 8. 测试数据的作用

`lerobot-record --policy.path` 保存的是策略执行轨迹，适合保存和复查：

- 摄像头画面。
- 状态和动作。
- 任务文本。
- 推理延迟和动作执行过程。

策略驱动的录制不会自动提供任务成功标签。成功、失败、碰撞和人工干预必须由操作者
在测试记录中逐 episode 标注。

## 9. 动作执行步数实验

固定同一组测试起点，分别测试：

```text
n_action_steps = 1
n_action_steps = 10
n_action_steps = 25
n_action_steps = 50
```

每次只改变一个值。LIBERO 上已知 50 明显差于 10；本地任务需要单独验证。

优先推荐从：

```bash
--policy.n_action_steps=10
```

开始。

## 10. 测试条件设计

至少覆盖：

| 条件         | 训练中是否出现 | 测试要求       |
| ------------ | -------------- | -------------- |
| 标准位置     | 是             | 检查基本能力   |
| 轻微位置偏移 | 是             | 检查插值泛化   |
| 新位置组合   | 否             | 检查独立泛化   |
| 光照变化     | 可选           | 检查视觉鲁棒性 |
| 初始关节偏移 | 可选           | 检查状态条件   |

每个条件中的物体初始位置必须预先定义并编号，不能根据模型表现临时调整。

## 13. 接受标准

安全门：

```text
无无人控制的持续碰撞
无关节超限
无电缆缠绕
急停可立即终止动作
```

性能门建议：

```text
训练分布位置：微调模型成功率达到项目设定阈值
独立位置：微调模型优于基础模型，且没有明显灾难性退化
平均完成时间：不显著高于基础模型
失败模式：可通过数据覆盖或参数调整解释
```

具体成功率阈值应由任务风险、物体成本和可用时间决定。不要只报告成功的 episode。

## 14. 失败分类

每个失败 episode 归入一个主类别：

```text
perception_failure
grasp_failure
slip_failure
wrong_target
collision
oscillation
stuck
timeout
language_misalignment
initial_state_out_of_distribution
hardware_error
```

统计每个类别的数量，再决定下一步。

## 15. 结果分析决策

### 训练集成功，测试集失败

优先处理：

- 增加测试位置附近的训练数据。
- 检查测试初始状态是否超出训练范围。
- 检查摄像头位置是否改变。
- 检查物体颜色、尺寸、反光是否变化。

### 抓取成功，放置失败

优先处理：

- 增加放置阶段的 demonstration。
- 扩大目标区域变化。
- 确保目标区域在 camera1 中清晰可见。
- 检查动作 chunk 是否在放置阶段被过早切换。

### 基础模型和微调模型都不动

优先检查：

- 动作维度或关节顺序。
- 状态归一化统计。
- 摄像头输入顺序。
- 训练数据 camera key、推理 camera key 和 `empty_cameras`。
- task text。
- `max_relative_target` 是否过小。
- `n_action_steps` 是否与训练不匹配。

### 动作抖动或连续振荡

尝试：

- `n_action_steps=10`。
- 降低推理频率或使用插值。
- 检查训练数据中的停顿和抖动。
- 检查策略输出后的 `max_relative_target` 截断是否符合预期。

## 17. 测试完成后的归档

至少保存：

- `train_config.json`
- 最终检查点的 `config.json`
- 模型权重
- 数据 train/val/test 哈希
- 测试 CSV 或 JSONL
- 策略执行录制的评估数据集
- 测试视频
- 失败案例清单
- 本次测试源码 commit 或归档校验值
- 最终报告

没有这些记录，结果不能被视为可复现。
