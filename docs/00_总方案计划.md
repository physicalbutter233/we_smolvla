# SmolVLA 项目总方案计划

## 1. 文档定位

本文件定义项目目标、范围、阶段、验收条件、目录结构和风险控制。

配套的五份指导书：

1. `01_部署项目指导书.md`
2. `02_仿真测试项目指导书.md`
3. `03_数据收集与格式处理项目指导书.md`
4. `04_微调项目指导书.md`
5. `05_本地微调结果测试指导书.md`

所有文档只提供操作指导和命令参考，不代表这些命令已经在当前机器上执行。

本项目的软件控制面统一为 LeRobot `0.4.3`、Python 3.10、Conda 环境
`lerobot_043`。机械臂校准、遥操作、数据录制、LIBERO 仿真、SmolVLA 微调、
SmolVLA 评估和真实机械臂策略测试全部在同一版本体系中完成。

## 2. 项目目标

在单台 Ubuntu 主机、单张 NVIDIA RTX 4070 SUPER 12 GB 显卡、一对 SO-100 或
SO-101 主从机械臂和固定摄像头的条件下，完成以下闭环：

1. 安装并验证 LeRobot `0.4.3`、SmolVLA、Feetech 硬件依赖和 CUDA 环境。
2. 在 LIBERO 仿真环境中验证 SmolVLA 推理链路、评估链路和训练链路。
3. 使用主从机械臂收集本地遥操作数据。
4. 将本地数据整理为 LeRobotDataset v3 格式并完成质量检查。
5. 基于 `lerobot/smolvla_base` 进行动作专家微调。
6. 在本地机械臂上比较基础模型与微调模型，形成可复现测试结果。

## 3. 项目范围

### 3.1 首轮范围

首轮只处理一个明确任务，例如：

```text
Pick up the blue cube and place it in the box.
```

首轮固定以下条件：

- 一台 SO-100 或 SO-101 follower。
- 一台对应的 SO-100 或 SO-101 leader。
- 固定摄像头数量、位置、分辨率和帧率。
- 固定桌面、光照、物体集合和初始区域。
- 固定任务文本。
- 固定 LeRobot 版本、模型版本和数据集版本。

### 3.2 首轮不包含

- 不在 12 GB 显存上做全参数大批量训练。
- 不在首轮引入多个机器人、多个任务或频繁变化的摄像头位置。
- 不把在线强化学习作为首轮目标。
- 不直接使用未经验证的网络视频数据替代本地演示数据。
- 不使用 LeRobot `0.4.3` 不支持的 LoRA/PEFT 训练接口。
- 不使用 `lerobot-rollout`，因为 LeRobot `0.4.3` 不提供该命令。

## 5. 软件版本基线

统一使用以下环境：

```text
conda 环境: lerobot_043
Python: 3.10.x
LeRobot: 0.4.3
源码目录: /path/to/we_smolvla
PyTorch: 2.8.0+cu128
Transformers: 4.57.6
torchcodec: 0.6.0
accelerate: 1.15.0
num2words: 0.5.14
数据集格式: LeRobotDataset v3.0
基础模型: lerobot/smolvla_base
LIBERO 测试模型: lerobot/smolvla_libero
```

版本固定规则：

- 不把另一个 LeRobot 版本安装到 `lerobot_043`。
- 记录 `git rev-parse HEAD`，若源码目录没有 Git 元数据，则记录压缩包来源和校验值。
- 记录 `python --version`。
- 记录 `python -m pip show lerobot torch transformers torchcodec accelerate num2words`。
- 记录 GPU 驱动版本和 `nvidia-smi` 输出。
- 记录模型和数据集 revision。
- 不在训练中途升级依赖。

磁盘口径说明：`df -h` 的“已用”列表示整个挂载点已占用的容量，不是某个文件的大小。
判断单个目录或文件大小应使用 `du`、`find` 或 `ncdu`。

## 6. 运行环境选择：Miniforge 与 Docker

首轮默认使用 Miniforge。原因是本项目需要直接访问两个 USB 串口机械臂和多个摄像头，
并需要运行校准、遥操作、录制、回放、LIBERO 渲染和模型推理。在宿主机使用
Miniforge 可以减少设备映射、权限和图形显示转发导致的额外故障点。

Docker 作为可选方案，适合以下范围：

- 只运行 LIBERO 仿真、数据处理或训练。
- 需要固定依赖和 CUDA 运行环境，以便复现实验结果。
- 已确认宿主机的串口、摄像头和权限能够稳定映射到容器。

如果使用 Docker 控制真实机械臂，容器至少需要处理：

- 使用 NVIDIA Container Toolkit，并通过 `--gpus all` 暴露 GPU。
- 映射两个串口，例如 `/dev/ttyACM0` 和 `/dev/ttyACM1`。
- 将宿主机 `dialout` 组 GID 映射给容器用户。
- 映射所有 `/dev/video*` 设备，并配置摄像头设备组权限。
- 在宿主机维护稳定设备路径和固定 USB 物理端口。
- 使用图形显示转发时，处理 X11/Wayland 权限和显示环境变量。
- 将项目目录、模型、数据集和输出目录以 volume 方式持久化到宿主机。

本项目不把 Docker 作为首轮唯一运行环境。若使用 Docker，必须同时记录镜像摘要、
容器启动命令、设备映射和宿主机驱动版本。

## 7. 推荐目录结构

项目根目录：

```text
/path/to/we_smolvla/
├── docs/
├── datasets/
│   ├── raw/
│   ├── processed/
│   └── eval/
├── models/
│   ├── smolvla_base/
│   └── smolvla_libero/
├── outputs/
│   ├── train/
│   └── eval/
├── logs/
├── reports/
└── scripts/
```

项目根目录同时是 LeRobot 源码目录。项目文档、数据、模型、训练输出、日志和报告
都统一保存在该目录下。LeRobot Python 包源码仍位于：

```text
/path/to/we_smolvla/src/lerobot
```

职责区分：

- `raw/`：原始录制或导入数据。
- `processed/`：清洗、拆分后的训练数据。
- `eval/`：最终测试产生的数据，不参与训练。
- `outputs/`：训练检查点和评估结果。
- `reports/`：人工测试记录、指标表和失败案例。

## 8. 总体数据流

```text
SO-101 follower + leader + cameras
        |
        v
lerobot-record
        |
        v
LeRobotDataset v3 原始数据集
        |
        v
质量检查、删除坏 episode、按 episode 拆分 train/val/test
        |
        v
lerobot-train + lerobot/smolvla_base + camera1/camera2 + empty_cameras
        |
        v
本地微调检查点
        |
        v
lerobot-record --policy.path=... 在独立测试条件下执行并录制
        |
        v
指标表、失败分析、是否迭代数据的决策
```

## 9. 阶段划分和验收门

### 阶段 0：环境和硬件验收

产物：

- `lerobot_043` Python 3.10 环境。
- LeRobot `0.4.3`、SmolVLA、Feetech、LIBERO 依赖。
- 可加载的 `lerobot/smolvla_base`。
- 可被识别并校准的 leader 和 follower。

验收：

- `nvidia-smi` 正常。
- `torch.cuda.is_available()` 为 `True`。
- `lerobot-info` 正常。
- `lerobot-find-port` 能找到两个机械臂串口。
- `lerobot-find-cameras opencv` 能找到全部摄像头。
- `lerobot-teleoperate` 可以连续稳定运行。

### 阶段 1：仿真验证

产物：

- LIBERO Spatial 小规模评估结果。
- 四 suite 标准评估结果，或按 suite 分批评估结果。
- 一次短训练冒烟测试和可重新加载的检查点。

验收：

- 仿真环境不崩溃。
- `lerobot-eval` 能产生 `eval_info.json`。
- `per_task`、`per_group` 和 `overall` 统计与实际任务数一致。
- 训练脚本能完成少量步数并保存检查点。
- 峰值显存和单步耗时被记录。

### 阶段 2：数据试点

产物：

- 5 至 10 个试录 episode。
- 视频、状态、动作、任务文本和统计信息检查结果。

验收：

- 视频和动作时间对齐。
- 摄像头无持续掉帧、黑屏、曝光突变或遮挡。
- 动作方向、维度、单位和归一化统计合理。
- 操作者能用统一策略稳定完成任务。

### 阶段 3：正式数据收集和格式化

产物：

- 正式训练集。
- 验证集。
- 独立测试集。
- 数据版本清单和哈希。

验收：

- 首轮建议至少 50 个有效 episode。
- 每个重要变化至少覆盖 10 个 episode。
- 训练、验证、测试按 episode 隔离。
- 数据集元数据为 LeRobotDataset v3。
- state 和 action 为 6 维。
- 已保存原始 `front`、`wrist` 数据副本。
- 已生成字段规范化的 `camera1`、`camera2` 数据副本，训练时不需要 `rename_map`。

### 阶段 4：微调

产物：

- SmolVLA 默认动作专家微调检查点。
- 训练日志。
- 显存、耗时、损失和恢复记录。

验收：

- 训练过程中无持续 OOM。
- 能从 `checkpoints/last/pretrained_model` 重新加载。
- 训练配置中记录的数据集、任务文本、camera mapping 和空摄像头数量正确。
- 不使用 LoRA/PEFT 参数，因为 LeRobot `0.4.3` 不提供对应训练器。

### 阶段 5：本地结果测试

产物：

- 基础模型和微调模型的对照结果。
- 成功率、耗时、碰撞、干预和失败分类。
- 可复现实验记录。

验收：

- 安全测试无失控碰撞。
- 微调模型在训练分布内达到设定目标。
- 微调模型在独立测试条件下得到记录，而不是只展示最佳 episode。
- 策略执行数据通过 `lerobot-record --policy.path=...` 保存。
- 结论、失败原因和下一轮数据修改明确。

## 10. 数据规模和训练规模

### 10.1 数据规模

首轮建议：

```text
任务数: 1
关键位置或变化: 5 个
每个变化: 10 个成功 episode
总有效 episode: 50
帧率: 30 FPS
单 episode 有效动作时长: 10 至 20 秒
```

如果任务更复杂，增加 episode 数量之前先检查：

- 物体初始位置。
- 物体姿态。
- 抓取点差异。
- 光照和反光。
- 机械臂初始姿态。
- 放置目标边界。

### 10.2 训练规模

12 GB 显存建议：

```text
per_device_batch_size: 1 或 2
precision: BF16，通过 --policy.use_amp=true
method: SmolVLA 默认动作专家微调
freeze_vision_encoder: true
train_expert_only: true
train_state_proj: true
```

LeRobot `0.4.3` 的 `lerobot-train` 每次循环执行一次前向、反向和
`optimizer.step()`。`--steps` 表示优化器更新次数，不是样本数，也不是
micro-batch 数。该版本没有训练器梯度累积 CLI 参数。

如果必须扩大有效批次，应优先使用具备更大显存的多卡环境。若要在本机实现梯度累积，
需要修改训练循环，不作为首轮方案。

## 11. 安全和操作规范

本地测试前必须执行：

1. 设置并验证急停装置。
2. 清空机械臂运动范围。
3. 使用较小的 `--robot.max_relative_target` 限制相对运动。
4. 首次策略执行时让物体远离夹爪或抬高机械臂。
5. 第一次运行必须有人值守。
6. 不从电线、玻璃、尖锐物体或人体附近开始测试。
7. 不长时间无人值守运行训练或推理。

建议初始安全参数：

```bash
--robot.max_relative_target=5
```

确认动作方向和幅度后，再逐步调整。

## 12. 风险登记表

| 风险           | 触发条件                               | 控制措施                                                         |
| -------------- | -------------------------------------- | ---------------------------------------------------------------- |
| 显存不足       | batch 过大、视频 token 过多            | batch 1 起步、BF16、关闭环境评估                                 |
| 内存不足       | DataLoader worker 过多、桌面程序占用大 | `num_workers=2` 起步、关闭大型程序                               |
| 串口不稳定     | 线缆或供电问题                         | 固定线缆、检查供电、使用稳定 USB 端口                            |
| 摄像头不同步   | USB 带宽不足、分辨率过高               | 使用不同 USB 控制器、640x480                                     |
| 训练数据过拟合 | 位置变化过少、测试集泄漏               | 按 episode 和位置拆分，保留独立测试集                            |
| 任务文本不一致 | 录制、训练、推理文本不同               | 将任务文本作为冻结变量                                           |
| 摄像头顺序变化 | 重插设备或重排字典                     | 固定物理位置、固定 camera key、每次测试核对                      |
| 动作尺度错误   | 单位、delta 和绝对动作不匹配           | 录制后检查状态和动作范围，先回放再训练                           |
| 数据字段不匹配 | 本地 camera key 与模型输入不同         | 优先使用 `camera1`、`camera2` 规范化副本，并设置 `empty_cameras` |
| 评估选择偏差   | 只测试成功案例                         | 固定测试协议，逐 episode 记录全部结果                            |

## 13. 冻结变量

## 15. 里程碑决策

```text
M0 环境验收 -> M1 仿真验收 -> M2 试点数据验收
-> M3 正式数据冻结 -> M4 微调验收 -> M5 本地测试验收
```

只有满足前一阶段的验收条件，才进入下一阶段。

如果 M2 失败，不继续扩大数据量；先修正摄像头、动作方向、操作策略和任务定义。

如果 M3 失败，不进入正式微调；先重录、删除坏 episode 或修改数据分布。

如果 M4 失败，不先改模型参数；先检查数据字段、camera key、`empty_cameras` 和预处理器。

如果 M5 失败，不发布结论；先分类失败 episode，再决定补数据、调整动作执行步数或重新训练。
